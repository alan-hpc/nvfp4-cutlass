第 0 步 · 前置：先修对，再修快

已完成epilogue TMEM 子分区 bug。 内核最初所有 shape 输出 cosine ≈ 0。用 one-hot 探针（A = I，输出第 r 行应精确等于 wdeq[:, r]）测出错误结构：整块 32 行的循环位移 {+96, −32}。

根因：epilogue 用 epilogue_warp_idx(0..3) 索引 SMEM 行块，但 tcgen05.ld 的 TMEM 子分区由 warp 绝对编号 mod 4 决定。本内核 非 epilogue warp 数为 3 + 8 = 11（非 4 的倍数），epilogue warp 绝对编号 11..14 → 子分区 3,0,1,2，恰好旋转一格。DeepGEMM 原版能这样写是因为它断言非 epilogue 线程数 == 128，epilogue 永远从 warpgroup 边界开始。

- epilogue_warp_idx * 32 * kSwizzleCDMode   // warp 在 epilogue 中的序号：错
+ subpartition_idx  * 32 * kSwizzleCDMode   // warp_idx % 4，硬件实际选的子分区

修复后 8/8 shape 全过（cosine 0.999925–0.999961）。这一步不是优化， 是优化的前提——对错误的内核做任何调优都是在优化噪声。

Swap-AB · decode 的对症设计（实施计划）

为什么 Swap-AB 才是 decode 的正解：粒度浪费源于「M-tile 固定 128 行 × 每 tile 单专家」。UMMA 的 M 维锁死 128，但 N 维可以 32/64/128/256。把操作数 对调——权重当 M 侧（128 行 tile 铺 model-N=1024/2048，天然整除）、 token 当 N 侧（tile N=32 起步）——粒度立刻从 128 行/专家 降到 32 列/专家。 更关键的是它直击本日志确立的楼层：

每 k-block 交付（decode, gate_up）现行（正向）Swap-AB
M 侧操作数A/BF16 32 KB（~97% 是废行）W/FP4 8 KB + SF
N 侧操作数W/FP4 16 KBA/BF16 8 KB（tile N=32）
合计~50 KB~17 KB

按 L2 交付楼层模型（每 SM 每 k-block ~1.0–1.2 µs 中交付占 0.6–0.8 µs），交付减 3× 预期把 decode gate_up 从 24.6 µs 压到 ~12–16 µs，与 MXFP8 链持平同时保住 0.9954 精度。tile 数（gate_up：8/专家 vs 现在 4/专家）仍在单 wave 内，不受罚。

实施清单（设备侧对称性已核实，DeepGEMM 有 swap-AB epilogue 参考实现）：

  1. 主循环操作数对调：packed-FP4 权重走现在 A0 的槽位（免 transform，TMA 直达）+ 权重 SF 走 SFA 槽（128×4 atom 布局两侧完全对称，现有 quantize_weight_nvfp4 产物可直接复用）；BF16 激活 TMA 进小 B-tile，transform 改写 B 槽 + SFB atom（不足 128 行的 SF 尾部 memset 归零）。
  2. Epilogue 转置存储：accumulator 是 (128 权重行 × N_tile token 列)，D 要 (tokens, model_N)——移植 DeepGEMM sm100_store_cd_swap_ab.cuh （144 行，warpgroup 协作转置 + 128B swizzle）。
  3. Host：tune_swap_ab 开关 + m_indices 对齐降到 N_tile（32）； 按 M 大小自动分派（M ≤ ~512/专家 → swap）。
  4. bring-up 按本日志既定纪律：先 one-hot 探针定位布局，再 cosine 门槛， 新 cache key 由 P1 头文件哈希自动保障。

轮次 4（存档）· 2-SM UMMA + multicast 设计（已被轮次 5 的分析撤销）

设计定型（读 DeepGEMM sm100_bf16 的 kNumMulticast=2 路径后）：SM100 的 正确形态不是"两个独立 CTA 共享 TMA 多播"，而是 cta_group::2 的 2-SM UMMA： cluster 内两个 CTA 组成一次 UMMA_M=256 的执行——A（激活）各持自己的 128 行（transform 各自照旧），W/SFB 一次多播进两个 SMEM。每 SM 每 k-block 交付 50→41 KB（−18%）， MMA 发射数减半，tensor 利用率随 M=256 上升。要点：Allocator2Sm、 leader-only tcgen05 发射、barrier 到达数 ×2（full_barriers.init(2) 等）、 scheduler cluster 化（N 对拆分）、epilogue 各 SM 排各自 128 行（现有 epilogue 不变）。

已落地：JIT 启动管道的 cluster 维度支持 （LaunchConfig::cluster_dim → CU_LAUNCH_ATTRIBUTE_CLUSTER_DIMENSION）。 进行中内核侧（impl 模板 kNumMulticast 化 + barrier 纪律 + 调度器）为下一工作块；预期 prefill 收益 ~10–18%（交付分量），把 8k gate_up 的 63→~53–57 µs，与 mxfp8 的 37 µs 之间剩余差距归于 1 B vs 2 B 的算法层选择。

解读（prefill）

  • 速度格局与 L2 交付模型一致：MXFP8 链路每元素只送 1 B 激活进 SM （我们送 2 B BF16），交付楼层天然减半；即便算上 36.5 µs 的独立量化 kernel （32k tokens, gate_up 档），两 kernel 链在深 K 上仍快 1.4–1.6×。down（K=512）上 量化开销占比升高，优势缩到 1.0–1.2×。
  • 精度格局是 10 倍的差距：同为 4-bit 权重，NVFP4（E4M3 连续 scale， block 16）保住 0.9954，MXFP4（UE8M0 只有 2 的幂，block 32）掉到 0.9544。 dual 的第二遍激活 MMA 把 single 的 0.0090 误差再压一半到 0.0046。
  • 结论保持仓库文档的判断：读两列。要吞吐、能吃 0.954 精度 → MXFP8×MXFP4;要 0.995 级精度的 4-bit 权重路径 → dual-NVFP4，代价是深 K 多 wave 下 ~1.5× 时延。（权重为 randn×0.5 合成分布；真实 LLM 权重的绝对 cosine 会不同，但两种 scale 格式的相对差距是结构性的。）

亚 wave 楼层（24.6 µs）：终局结论（O9 实验后）

「双 tile 交错」的廉价等价实现——O9 · 2 CTA/SM 共驻——已实施并测量： 瘦身配置（BLOCK_N=128, BLOCK_K=64, 4 transform warps, cd64, 单 epilogue stage）把 SMEM 压到 ~107 KB、TMEM 压到 256 列、寄存器留在预算内，296-CTA 网格下两个 CTA 真实共驻 且正确性全过。但：

这是整轮调查最有分辨力的否定：若每 k-block 的 ~1 µs 是可隐藏的空闲时延 （链上气泡），共驻的第二条链应能填进去——它完全没有。可被两条链共享而不加速的，只能是 被占用的每 SM 资源。对账：每 k-block 每 SM 搬运 50 KB（A/BF16 32 KB + W 16 KB + SFB 2 KB）；亚 wave 下 128 SM × 50 KB ÷ 1.19 µs ≈ 5.4 TB/s 聚合 L2 读——与 ncu 的 「L2 13.2%」（≈5.3 TB/s）严丝合缝。

楼层的物理身份：每 SM 的 L2→SMEM 交付通道。 每 k-block 50 KB 中 32 KB 是 BF16 激活——这正是 fused dual-NVFP4 设计自愿支付的代价 （每元素 2 B 进 SM，换取不在全局内存物化量化激活）。它解释了全部否定结果：加深管线、 加倍 warp、重排发射、共驻 CTA，没有一个能减少要搬的字节。要击穿它只有两类办法： ① 换算法（预量化 A → 放弃本 kernel 的存在前提）；② 提高 A 的复用（更大的 N tile 让同一 份 A 服务更宽的输出——BLOCK_N=256 已是 TMEM 上限，除非 UMMA_N 拆分重构）。 在本算法与本硬件预算内，24.6 µs 即楼层。

剩余可做但收益有限：prologue 缩短（~4–5 µs 截距的一部分，攻小 K shape）。 O9 的三个旋钮（tune_block_k / tune_epilogue_stages / set_num_sms 超额网格）保留为 API 面——它们已验证正确，只是在此工况下无收益。
